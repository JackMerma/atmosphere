Atmosphere

Upload a rigged humanoid 3D model, describe a motion in plain language, and watch an AI pipeline pick real, judged poses from a motion-capture library and animate your model's own joints with them.

What the app is made of

Three pieces, in order: a 3D viewport (upload, direct joint dragging, playback, the tracking camera), a configuration panel (Physics and Motion dials), and a small server layer — two API routes that are the only place the OpenAI and Jev keys ever touch, since everything else runs in the browser.

Nothing is generated from a blank page. Every pose that ends up in an animation is a real pose, pulled from a library harvested out of real motion-capture animation files, chosen by an AI judge rather than invented by one.

One action, traced through the code

Reference route (not toured live this session)

  1. Entry — components/MotionSection.tsx → lib/animator.ts
    Where the prompt and the three Motion dials live; animator.ts is the function that orchestrates everything below once you press Generate.
  2. Logic — lib/plannerClient.ts → app/api/motion/plan/route.ts, then lib/libraryChoice.ts → app/api/motion/rank/route.ts
    The plan comes out of OpenAI; each planned pose is measured against public/poseLibrary.json (296 real poses), and the resulting shortlist is photographed on the mannequin (lib/mannequin.ts) before Jev picks one.
  3. Result — lib/settle.ts → lib/animations.ts / lib/db.ts → components/PlaybackDriver.tsx
    Every winning pose passes through settlePose (limits + collision) before it's saved; Play walks lib/timeline.ts frame by frame.

To change this, start here

  • Change how many poses survive the first filter, or how many Jev compares at once → the three Motion dials in components/MotionSection.tsx, read by lib/libraryChoice.ts.
  • Expand which motions work well (today: jumping, sitting, walking) → not code, data: drop more .fbx files into poses/ and re-run npx tsx scripts/harvest.ts (see docs/status.md, item 4).
  • Tighten or loosen how "human" a pose looks → the three Physics dials, read by lib/jointLimits.ts, lib/collision.ts, and lib/ikChain.ts inside lib/settle.ts.

A practice to reuse

Real project decision

The original pipeline asked Jev for a 0–1 number ("how well does this pose match?") and climbed that signal uphill. docs/decisions.md records why that was dropped: the number came back low and barely moved (0.1–0.5 for poses that looked right at a glance) — climbing a signal that flat, with random candidates, is close to random search. The evidence came from running it against the real API, not from suspecting it.

The fix: instead of asking for a number, ask Jev to choose — "which of these is best," with the current pose as one more option. It's the same question Jev answers well, one call per round instead of one per candidate, and it never makes things worse because the current pose can always win.

The practice that repeats throughout this project (and that this very session also lived through, reopening scope.md/prd.md/spec.md once the real, working build no longer matched the planned mechanism): when real evidence contradicts an assumption — yours or an agent's — you correct the assumption, you don't argue with it. That applies equally to a call to an external API and to a planning document.

How to run it again

npm install, then npm run dev, open http://localhost:3000. Requires OPENAI_API_KEY and the Jev key in .env.local.
