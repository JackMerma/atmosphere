Atmosphere

El plano técnico: sube un modelo rigged, el navegador lo lee directo, y dos rutas de servidor delgadas hablan con Jev y Gemini para decidir el movimiento.

Cómo funciona, en palabras simples

Abres una sola página. Subes un archivo 3D que ya tiene esqueleto — algo que descargaste o sacaste de una librería gratuita como Mixamo. El navegador lee ese archivo directamente (sin pasar por ningún servidor) y encuentra cada hueso que puede rotar. Puedes girar el modelo completo, o activar "Lock" y arrastrar huesos individuales para ver qué hacen.

Luego escribes una frase describiendo una secuencia de poses. Esa frase va a Gemini, que la parte en una lista corta de poses individuales. Por cada pose, la app toma una foto de la vista 3D actual y se la manda a Jev con una pregunta: "¿esto coincide con la pose?". Si Jev dice que no, pregunta "¿qué hueso debería moverse, y hacia dónde?". La app hace ese ajuste chiquito, toma otra foto, y vuelve a preguntar — hasta 10 veces por pose. Eso es "convergencia": empujoncitos pequeños hacia el objetivo, como ir acomodando un muñeco a mano.

Cuando todas las poses están listas, el navegador interpola suavemente entre ellas — eso ya es solo matemática de animación, sin IA — y obtienes un loop. Todo lo generado (el modelo, sus huesos, cada animación) se guarda en el propio navegador (IndexedDB) para que siga ahí si recargas.

Por qué así: no hay base de datos de servidor ni cuentas porque nada necesita compartirse entre personas. Solo hay un par de rutas de servidor pequeñas porque las API keys de Jev y Gemini no pueden vivir en código del navegador — todo lo demás corre en el cliente.

El recorrido por el sistema

  1. Abre la app → Next.js renderiza el dashboard vacío.
  2. Sube .glb/.gltf → GLTFLoader (three.js) lo parsea en el navegador, sin servidor.
  3. El parser de articulaciones extrae cada hueso (nombre + jerarquía). Si falla o no hay huesos → error.
  4. Modelo + articulaciones se guardan en IndexedDB; se renderiza vía React Three Fiber.
  5. Lock + hover/drag — todo en el cliente, sin red.
  6. Prompt de Motion → /api/motion/decompose → Gemini → lista ordenada de poses.
  7. Por cada pose: screenshot → /api/motion/step → Jev (Noul + Choice) → ajuste → repetir hasta 10 veces.
  8. Poses convergidas = keyframes → interpolación suave en el cliente.
  9. Resultado → nueva entrada en Animations history (IndexedDB).
  10. Play reproduce la animación activa en loop.

Dónde corre y cómo probarlo

Local, sin deploy. npm install → npm run dev → http://localhost:3000. Requiere TYPESAFE_API_KEY y GEMINI_API_KEY en .env.local (ya en .gitignore). Para la demo: sube un .glb rigged, mueve un hueso con Lock, abre Motion con un prompt multi-pose, graba la convergencia, presiona Play. Video + repositorio público en GitHub — sin URL desplegada para esta PoC.

Componentes

Upload y parser de articulaciones prd.md › Model Upload & Joint Mapping

File input → GLTFLoader parsea el modelo en el navegador → se camina el grafo de escena buscando nodos THREE.Bone → lista ordenada de articulaciones. Se guarda en IndexedDB al tener éxito; error visible si falla o no hay huesos.

Viewport y manipulación manual (Lock) prd.md › Manual Joint Exploration

<Canvas> de r3f. El estado de Lock cambia el comportamiento del puntero: rotación completa (estilo orbit) vs. raycasting por hueso (hover resalta, arrastrar rota ese hueso).

Orquestación de Motion prd.md › Motion Generation

Decomposición: /api/motion/decompose llama a Gemini con un schema JSON ({ poses: string[] }).

Convergencia: por cada pose, el cliente renderiza el canvas actual, lo manda junto al texto de la pose y la lista de articulaciones a /api/motion/step, que llama a Jev (Noul, luego Choice si no coincide) y devuelve el ajuste. El cliente lo aplica y repite, tope de 10 iteraciones.

Historial de animaciones y reproducción prd.md › Playback

Cada generación completa se agrega a una lista (Zustand + IndexedDB), más reciente primero, etiquetada "Animation N". Seleccionar una la activa; Play interpola y reproduce en loop sus keyframes.

Capa de persistencia prd.md › States and Boundaries

lib/db.ts envuelve IndexedDB (vía idb) con tres almacenes: model, animations, metadata. Se lee al cargar la app para restaurar sin re-subir; se escribe en cada cambio.

Modelo de datos

model — { fileBlob, fileName, joints: [{ name, id, parentId }] }. Un solo registro, se reemplaza al subir un modelo nuevo.

animations — lista de { id, label, createdAt, keyframes: [{ poseDescription, jointAngles }] }. Se agrega, nunca se sobrescribe.

Lo que NO persiste: selección de Lock/hover, estado de modales, indicadores de carga — se reinician al recargar, y está bien así.

Modos de falla importantes

Archivo sin esqueleto / falla al parsear → mensaje de error en la subida, nada se guarda, se puede reintentar.
Jev o Gemini falla o da timeout a mitad de la generación → se detiene, mensaje de error, no se guarda una entrada de historial parcial/corrupta.
La convergencia no llega a coincidir en 10 iteraciones → se usa la mejor pose alcanzada como keyframe y se sigue con la siguiente pose, sin trabar toda la generación.

Qué se simplificó y por qué

IndexedDB en el navegador en vez de base de datos de servidor — nada se comparte entre usuarios.

Opciones de ajuste acotadas (no ángulos continuos) — Jev solo responde Choice/Score/Noul.

Bucle de convergencia con tope fijo (10 iteraciones) — costo y tiempo predecibles para una PoC.

Descomposición del prompt vía una llamada a Gemini en vez de un parser manual — más robusto ante frases variadas.

Sin generación de apariencia — el modelo subido se usa tal cual; la idea de capas por foto queda diferida.

Decisiones y asuntos abiertos

Pivote del maniquí propio a un modelo subido ya rigged — decidido en esta sesión; toda la arquitectura de arriba parte de esa base.
Jev no puede devolver valores continuos — la incertidumbre real que se resolvió en esta sesión: se asumía que se le podía pedir un ángulo directo; revisar docs.typesafe.ai mostró que solo existen Choice/Score/Noul, lo que llevó al diseño de convergencia iterativa en vez de una sola llamada.
Esto es justo lo que el aprendiz quería entender de Jev, y ahora está basado en la API real verificada, no en una suposición.
Costo por imagen de Jev es una estimación, no un número oficial — verificar con la primera llamada real (usage.input_tokens) al empezar el build.
Nombre exacto del modelo de Gemini — confirmar contra la lista de modelos vigente al iniciar el build.
Opciones de eje/dirección por articulación para el Choice de Jev — este spec asume un conjunto chico por defecto; el conjunto correcto depende de cómo los modelos rigged típicos (ej. exports de Mixamo) orientan sus huesos, más fácil de confirmar inspeccionando un modelo real al inicio del build que de adivinar más aquí.
Tope de iteraciones (10) y umbral de convergencia — valores de partida, ajustables una vez visible el comportamiento real (heredado de prd.md › Open Questions).
